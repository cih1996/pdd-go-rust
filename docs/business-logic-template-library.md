# 业务逻辑与模板库改造说明

## 1. 目标

这份文档用于记录当前项目已经落地的核心业务逻辑，方便后续继续改造模板系统。

当前重点有两件事：

1. 明确现在任务执行、识别、上传、明细记录到底怎么跑。
2. 为后续“不同设备使用不同模板库”改造预留清晰的设计方向。

## 2. 当前服务分工

当前 Windows 打包后的整体运行形态是 4 个服务放在同一目录协同工作：

- `unified-server.exe`
  - 主业务服务
  - 负责设备控制、任务执行、模板管理、运行时状态、前端接口
- `adapter-rs.exe`
  - 上游协议适配器
  - 负责取任务、提交结果、上传截图
- `opencv-server.exe`
  - OpenCV HTTP 服务
  - 负责模板图匹配
- `ocr-server.exe`
  - OCR HTTP 服务
  - 负责 OCR 文本识别

前端是 `frontend/dist` 静态资源，由主业务服务对外提供页面。

## 3. 当前任务执行主链路

### 3.1 整体流程

单台设备运行时，核心链路如下：

1. 设备从适配器领取任务。
2. 主业务按任务中的 SKU 列表逐个执行。
3. 每个 SKU 会先生成实际打开的 URL。
4. 通过 ADB 执行打开链接。
5. 等待页面稳定后进入识别循环。
6. 每轮循环只截图一次。
7. 按固定顺序检查模板命中情况。
8. 根据命中类型决定继续点击、释放、停机或成功。
9. SKU 执行结束后，先记录本地执行明细。
10. 整个任务结束后，再统一提交给适配器。

### 3.2 每轮识别顺序

每轮截图后的模板识别顺序固定如下：

1. `account_risk`
2. `fail_release`
3. `click_image`
4. `success_image`

这四类模板的含义如下：

- `account_risk`
  - 命中表示账号风控
  - 当前任务失败
  - 当前设备会切换 URL 模板或停机
- `fail_release`
  - 命中表示当前任务释放
  - 当前任务失败
  - 设备可以继续接下一单
- `click_image`
  - 命中后执行点击
  - 点击后继续下一轮识别
- `success_image`
  - 命中表示当前 SKU 成功
  - 当前 SKU 执行完成

### 3.3 点击图与成功图的截图规则

当前业务已经明确成下面这条规则：

- 当第一次命中 `click_image` 时：
  - 保留当前这张“点击前大图”
  - 再执行点击
- 如果同一个 SKU 后续又再次命中 `click_image`
  - 不覆盖第一次保存的点击前大图
- 当后续某一轮命中 `success_image` 时：
  - 再保留一张“成功图当轮大图”

所以一个成功 SKU 最终可能上传两张图：

1. 第一次点击前的大图
2. 成功图命中时的大图

如果从未命中过点击图，那么通常只保留成功图。

### 3.4 当前 SKU 只匹配一次规则

模板支持单独配置“本任务仅匹配一次”。

规则如下：

- 某模板如果勾选了 `match_once_per_task`
  - 在当前任务的当前 SKU 中只要命中过一次
  - 后续循环里该模板不再参与匹配
- 领取新任务后重新开始，不继承上个任务状态
- 单独调试里的 5 轮循环，也遵循相同规则

## 4. 当前模板系统

### 4.1 模板基础字段

当前模板记录至少包含这些核心信息：

- 模板名称 `label`
- 模板类型 `template_type`
- 识别引擎 `recognition_engine`
- 优先级 `priority`
- OCR 期望文本 `expected_text`
- OpenCV 图片 `image_name` / `image_path`
- 阈值 `threshold`
- 方法 `method`
- 灰度开关 `grayscale`
- 裁剪区域 `crop`
- 是否启用 `enabled`
- 失败释放前置条件 `requires_click`
- 本任务仅匹配一次 `match_once_per_task`

### 4.2 模板类型

当前模板统一存放在同一个模板库中，但按用途分为四类：

- 账号风控模板
- 失败释放模板
- 点击图模板
- 成功图模板

### 4.3 模板优先级

同一类模板内部按如下顺序匹配：

1. `priority`
2. `created_at`

也就是说：

- 先看大类顺序
- 再看同类模板内部优先级

### 4.4 OpenCV 模板规则

OpenCV 模板要求必须有有效图片。

当前已经支持：

- 模板图通过前端上传
- 打包导出时带出图片
- 导入时把图片恢复回模板目录
- 中文路径下正确读取模板图
- 同一轮截图只上传一次大图到 OpenCV 服务
- 小图按最多 10 张一批批量匹配
- 任一张命中后立即返回

### 4.5 OCR 模板规则

OCR 模板当前走 `ocr-server` HTTP 接口，不再使用后端内置 OCR。

同一轮截图中的 OCR 规则如下：

- 只有本轮模板里存在 OCR 模板，才会触发 OCR 请求
- 同一轮截图只做一次 OCR
- 本轮所有 OCR 模板复用同一个 OCR 结果

这条规则不能破坏，否则性能会明显下降。

### 4.6 OCR 条件语法

当前 `expected_text` 已支持以下语法：

- `A&B`
  - 表示多个条件都必须存在
- `A&!B`
  - 表示必须存在 `A`
  - 且必须不存在 `B`

例如：

- `店铺优惠&领券`
  - 识别结果里必须同时存在 `店铺优惠` 和 `领券`
- `店铺优惠&!领取`
  - 识别结果里必须存在 `店铺优惠`
  - 且不能出现 `领取`

### 4.7 OCR 点击坐标规则

OCR 模板命中后，点击坐标不是取整张图，而是按规则取命中区域：

- 多条件匹配时，点击坐标以第一个正向条件为准
- 负向条件 `!xxx` 只参与判定，不参与取点击框
- 如果 OCR 把一个词拆成多个片段，后端会做窗口拼接匹配

例如：

- `店铺优惠&!领取`
  - 点击坐标跟随 `店铺优惠`
  - `领取` 只负责做排除判断

### 4.8 失败释放前置条件

失败释放模板支持单独配置 `requires_click`。

含义如下：

- 只有当前 SKU 之前已经命中过点击图并发生点击
- 该失败释放模板才参与匹配

这个能力只针对单个模板，不是全局规则。

适合处理“必须先点某处，后面某个失败释放图才有意义”的场景。

## 5. URL 模板与设备执行规则

当前 URL 模板已经支持设备级配置，但识别模板还没有设备级隔离。

### 5.1 URL 模板现状

当前已经支持：

- 系统中维护全局 URL 模板列表
- 每台设备可勾选“自己使用哪些 URL 模板”
- 设备启动后从自己的第 1 个 URL 模板开始
- 任务中如果触发账号风控
  - 自动切换到该设备的下一个 URL 模板
- 如果该设备可用 URL 模板全部风控
  - 设备自动停止
- 重新启动设备后
  - URL 模板轮换从第 1 个重新开始

### 5.2 ADB 打开 URL 规则

当前 URL 打开方式是直接执行完整 ADB shell 命令，并且：

- 对 URL 中的 `&` 做了 shell 转义
- 会把实际执行的完整 ADB 命令记录到执行明细里

这样前端可以直接展开查看和复制，方便排查跳转问题。

## 6. 运行时记录与排查能力

### 6.1 执行明细

当前执行明细已经包含这些排查信息：

- 命中的模板类型
- 模板名称
- 模板 ID
- 实际执行的 ADB shell 命令
- 失败释放模板上下文
- 适配器返回的截图 URL

### 6.2 当前任务执行进度

设备与任务区域的当前执行进度，已经支持显示最近命中的模板信息：

- 模板名称
- 模板类型
- 识别引擎

这样不再只是显示“命中点击坐标”，而是能看出到底是哪一个模板在触发。

### 6.3 模板测试

模板管理测试页当前支持：

- OCR 命中全文展示
- 多条件命中明细
- 每个条件对应的实际命中来源
- 预览图绘制命中框

这里需要注意：

- 多条件 OCR 的点击框显示的是首个正向条件的点击区域
- 其他正向条件主要用于判定和辅助展示

## 7. 数据持久化

当前已经把容易丢失的数据迁到 AppData 目录，避免覆盖打包目录时丢数据。

### 7.1 主业务持久化

主业务默认运行时目录：

- `%LOCALAPPDATA%\PddGoRust\unified-server`

持久化内容包括：

- SQLite 数据库
- 模板图
- 调试截图

### 7.2 适配器持久化

适配器截图默认目录：

- `%LOCALAPPDATA%\PddGoRust\adapter-rs\captures`

这样执行明细中的截图即使服务重启后也能恢复。

### 7.3 旧数据迁移

主业务启动时会尝试从旧 `.runtime` 目录迁移：

- 数据库
- 模板图
- 调试截图

用于兼容旧版本升级。

## 8. 打包与发布

当前打包策略如下：

- 四个服务分别打包
- 所有可运行文件汇总到 `dist/windows-bundle`
- 生成 `start-all.bat`
- 单独打包某个服务后，会自动同步到 `windows-bundle`

这样可以直接把 `windows-bundle` 整体发给用户覆盖更新。

## 9. 当前模板系统的局限

目前识别模板库仍然是“全局共享”模型。

这意味着：

- 所有设备共用同一套识别模板
- 只能通过模板类型、优先级、前置条件、启用状态来控制行为
- 不能做到“设备 A 用一套点击图，设备 B 用另一套点击图”

这已经成为后续扩展的主要限制。

## 10. 后续改造成设备级模板库的建议

目标不是简单给模板加一个设备 ID，而是要支持“模板库”概念。

建议把后续设计拆成三层：

### 10.1 模板库层

新增“模板库”实体，例如：

- `library_id`
- `name`
- `description`
- `enabled`

含义：

- 一套模板库就是一组可复用的识别模板集合

### 10.2 模板层

模板从“全局模板”改为“归属某个模板库的模板”：

- 一个模板只属于一个模板库
- 模板排序、导入导出、启用停用都在模板库内部处理

这样才能做到真正隔离。

### 10.3 设备绑定层

设备不直接绑定单个模板，而是绑定一个或多个模板库：

- 设备 A -> 模板库 1
- 设备 B -> 模板库 2
- 设备 C -> 模板库 1 + 模板库 3

运行时按设备拿到自己的模板集合，再进入现有识别链路。

## 11. 推荐的改造顺序

为了减少一次性大改，建议按下面顺序推进：

1. 新增模板库数据模型
2. 给模板增加 `library_id`
3. 前端模板页先支持按模板库切换查看
4. 设备页新增“设备绑定模板库”
5. 任务执行链路改为 `按设备加载模板集合`
6. 调试页支持“按设备模板库”或“手选模板库”运行
7. 导入导出升级为“按模板库导入导出”

## 12. 改造时的兼容建议

为了不影响现有用户数据，建议做兼容迁移：

- 系统升级后先自动创建一个默认模板库，例如：
  - `默认模板库`
- 把当前所有历史模板迁移到这个默认模板库
- 所有设备默认绑定这个默认模板库

这样老数据不需要人工整理也能继续跑。

## 13. 改造时必须保留的旧能力

设备级模板库改造时，下面这些规则必须保留：

- 每轮只截图一次
- OCR 每轮只请求一次并复用结果
- 模板匹配顺序仍然固定为四大类顺序
- 模板内部仍按优先级和创建时间排序
- 点击图只保留第一次点击前截图
- 成功图命中后仍保留成功图截图
- `requires_click` 仍然只作用于单个失败释放模板
- `match_once_per_task` 仍然按任务内模板维度生效
- OCR `&` / `!` 语法继续保留

## 14. 最终建议

如果后续要做“不同设备采用不同模板库”，建议优先选择下面这条路线：

- 先做“设备绑定模板库”
- 不要先做“模板直接绑定设备”

原因是：

- 模板直接绑设备会导致模板重复复制很多份
- 后期维护、导入导出、排序、调试都更乱
- 模板库模式更适合多设备、多场景、多商家并存

如果后续继续实现这套能力，可以以本文件作为总说明，再补两份细化文档：

1. 数据结构迁移方案
2. 前端交互改造方案
